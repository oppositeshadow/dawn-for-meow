# 规划与验收方 × 实施方协作开发固定流程

> 性质：本文件是《喵星破晓》多角色协作的持久协议，用于跨会话恢复工作方式。
> 适用角色：规划与验收方、实施方、用户（最终决策与调度）。
> 重要：本文件只规定“怎么协作”，不保存会变化的当前任务。当前任务永远从 `项目全量任务清单与协作节流指南.md` 顶部短指针和 `协同工作计划与验收反馈.md` 当前任务段读取。

## 1. 三份文件的职责

### 1.1 `AGENTS.md`：项目总规则入口
规定项目权威文档顺序、开发铁律和协作入口。任何角色开始工作前先遵守它。

### 1.2 `项目全量任务清单与协作节流指南.md`：长期路线图 / 任务索引
由规划与验收方用于：
- 查看“最后通过 / 当前任务 / 下一候选”短指针；
- 选择任务 ID；
- 查看任务目标、范围、验收门槛和推荐顺序；
- 在验收后同步任务状态和短指针。

它不是实施方的正式验收交接渠道，也不能替代第一份协同文档里的任务计划或验收结果。

### 1.3 `协同工作计划与验收反馈.md`：唯一正式工作台
这是规划与验收方和实施方之间的正式交接文件，也是实施方每轮应主要读取的文件。

每个任务固定包含三类内容：
1. **任务计划**：由规划与验收方写；
2. **实施记录**：由实施方写；
3. **验收反馈**：由规划与验收方写。

任何任务的“通过 / 退回 / 返修要求”如果只出现在聊天或第二份路线图里，而没有写入本文件的验收反馈，就不算完成正式交接。

## 2. 角色边界

### 2.1 规划与验收方
规划与验收方负责：
- 从长期路线图选择当前唯一任务；
- 把任务展开并写入 `协同工作计划与验收反馈.md`；
- 明确目标、作用域、文件白名单、禁止范围、测试矩阵和完成门槛；
- 在实施方提交后独立审查 commit / diff；
- 复核或复跑任务要求的测试、静态审计和必要真机证据；
- 将每一轮验收结果写入第一份协同文档的“验收反馈”；
- 退回时给出单点、最小、可执行的返修要求；
- 通过后更新长期路线图状态与短指针，再规划下一任务。

规划与验收方不替实施方填写实施记录，不把自己的验收结论只留在聊天里。

### 2.2 实施方
实施方负责：
- 只按第一份协同文档中当前任务的计划实施；
- 开工时将实施状态改为“实施中”；
- 严格遵守文件白名单、禁止范围和既定契约，不自行扩需求；
- 完成代码、测试和计划要求的验证；
- 只填写“实施记录”，不填写或改写“验收反馈”；
- 实施记录完成后把状态改为“待验收”，提交 Git commit，然后停止；
- 若被退回，只读取第一份协同文档最新验收反馈，按最小返修要求继续同一任务；
- 未经“验收通过”不得开始下一任务。

### 2.3 用户：最终决策与调度
用户负责：
- 决定是否开始某轮任务、是否调整优先级或取消任务；
- 在出现产品方向冲突时做最终取舍；
- 可以要求规划与验收方进行规划或验收，也可以要求实施方开始实施；
- 用户的明确新指令优先于既有路线，但应由规划与验收方把变化正式写回协作文档后再执行。

## 3. 每轮标准状态机

固定流转：

`待规划 → 已下发/待实施 → 实施中 → 待验收 → 通过`

若验收失败：

`待验收 → 验收退回（第 N 轮） → 返修中 → 待验收（第 N+1 轮）`

规则：
- 同一任务未通过前，任务 ID 不变；
- 不得因为测试大部分绿色就提前进入下一任务；
- 每次退回只处理验收反馈列出的最小返修范围；
- 只有规划与验收方在第一份协同文档明确写出“验收通过”，该任务才正式关闭。

## 4. 规划方下发任务的固定流程

### 4.1 恢复上下文
新会话或继续项目时按最小读取顺序：
1. 读 `AGENTS.md`；
2. 读本文件；
3. 读 `项目全量任务清单与协作节流指南.md` 顶部“最后通过 / 当前任务 / 下一候选”；
4. 只读第二份文档中当前任务 ID 对应的小节；
5. 读 `协同工作计划与验收反馈.md` 当前任务计划、最新实施记录和最新验收反馈。

除非发生契约冲突或需要追溯历史，不重读整份数千行协同历史。

### 4.2 选择任务
- 优先处理“当前任务”；
- 当前任务处于返修状态时，只继续返修，禁止选择下一候选；
- 只有当前任务通过后，才从“下一候选”或路线图推荐顺序选择下一项；
- 高风险状态边界一轮只处理一个：数据库状态机、人口守恒、原子事务、离线时间推进、随机/幂等语义必须谨慎拆分；
- 直接配套的 Schema、前端类型、对应测试和准确修订记录可在不扩大风险时随主任务合并。

### 4.3 写入正式任务计划
规划与验收方必须把任务计划写进 `协同工作计划与验收反馈.md`，至少包含：
- 阶段 / 任务 ID / 任务名称；
- 当前状态；
- 任务性质与目标；
- 选择理由；
- 作用域登记；
- 前置基线；
- 唯一实现契约；
- **允许修改的精确文件白名单**；
- **禁止修改的范围和禁止手段**；
- 强制测试矩阵；
- 验收命令；
- 预期或实测基线说明；
- 完成标志；
- 实施记录空位；
- 验收反馈空位。

写完后，实施方才获得本轮正式实施依据。

## 5. 实施方实施与提交规范

实施方只依据当前任务计划工作。

实施记录固定尽量只写六项：
1. **状态**；
2. **实际修改文件**；
3. **核心行为与边界**；
4. **新增 / 修改测试**；
5. **验证命令与最终数字**；
6. **遗留风险**。

要求：
- 绿色测试只写汇总数字，不粘贴完整日志；
- 失败时只记录失败测试名、关键报错与复现命令；
- 测试不得硬编码可调平衡值，应从权威常量 / 种子推导；
- 不删除、跳过、弱化测试来换绿色；
- 不修改白名单之外的文件；若发现必须越界，停止并记录原因，由规划与验收方重新规划；
- 完成后将状态改成“待验收”，提交 Git commit，并停止，不自行进入下一阶段。

## 6. 验收方独立验收固定流程

### 6.1 验收输入
每轮优先只看：
1. 当前任务计划；
2. 实施方本轮 commit / diff，按白名单审查；
3. 实施记录中的测试与验证数字。

必要时再读取真实实现调用链、权威文档或历史验收记录。

### 6.2 验收检查顺序
1. **范围**：是否只改允许文件，有无夹带下一阶段或无关重构；
2. **契约**：实现是否真的满足任务计划，不只看测试是否绿色；
3. **证据质量**：测试是否使用真实 ORM 字段、真实持久化状态和正确夹具，是否存在 identity map、假字段、漏快照等“假绿色”；
4. **作用域**：母星 / 每星球 / 存档级是否符合工程规范，跨槽跨星是否隔离；
5. **确定性与幂等**：在线 / 离线、分段 / 长区间、重载 / 重复调用是否满足任务门槛；
6. **数值真源**：若涉及数值，核对 `数值平衡表.md → static JSON → balance.py` 三处同步；
7. **测试与审计**：按计划复核专项、组合、全量、接口账本、文档声明、静态总检、`git diff --check`，以及任务要求的真机证据；
8. **文档真实性**：不得把“只读规划器 / 运行时零调用”写成“玩法已生效”。

测试绿色不是自动通过条件；缺少关键证明也必须退回。

### 6.3 验收结果必须写入第一份文档
规划与验收方必须在 `协同工作计划与验收反馈.md` 当前任务的“验收反馈”中写明：
- 第几轮验收与日期；
- 结论：通过 / 退回；
- 独立实测数字；
- 差异与契约核对；
- 问题清单（带优先级和具体文件 / 位置 / 原因）；
- 最小返修范围；
- 禁止扩大范围；
- 通过后的残余风险。

**这是实施方下一轮唯一正式返修依据。**

## 7. 验收退回规则

若不通过：
- 不创建新任务；
- 不进入下一候选；
- 不让实施方自由“顺便修”；
- 规划与验收方把问题压缩成最小可验证返修；
- 明确“只允许修改哪些文件”；
- 明确“哪些已经通过，不得重写”；
- 保持原任务 ID，在第一份文档追加“第 N 轮验收”；
- 长期路线图可同步为“第 N 轮验收退回”，但第一份文档仍是正式交接源。

实施方返修完成后再提交新的 commit，进入下一轮验收。

## 8. 验收通过规则

若通过，规划与验收方应按顺序：
1. 在第一份协同文档写正式“验收通过”及独立证据；
2. 将当前任务状态关闭；
3. 更新 `项目全量任务清单与协作节流指南.md`：
   - 当前任务改为已完成；
   - “最后通过”指向本任务；
   - “当前任务”指向下一项；
   - “下一候选”顺延；
4. 如任务影响权威开发文档，只更新真实受影响内容；
5. 再为下一任务写新的正式计划。

**不能先下发下一任务、后补上一任务验收。**

## 9. Git 提交边界

建议每个完整循环形成清晰的提交边界：
- **计划提交**：规划与验收方写任务计划；
- **实施提交**：实施方完成功能 / 测试 / 实施记录；
- **验收提交**：规划与验收方写验收反馈；若通过，同时更新长期路线图短指针；若退回，写最小返修要求。

验收时以实施提交的 diff 为主要审查对象，不把历史累计差异误认为本轮授权范围。

## 10. 上下文与额度节流

遵循长期路线图中的节流原则：
- 使用固定任务 ID，不重复叙述整个项目；
- 每轮只保留最小交接包；
- 验收只优先读取任务计划、diff、实施记录；
- 绿灯只记录汇总数字；
- 稳定事实写入仓库文件，不依赖聊天记忆；
- 当前动态状态只维护在长期路线图短指针和第一份协同文档，不写死在本文件。

## 11. 冲突处理优先级

若协作文件之间发生冲突：
1. 数值 / 模型 / 接口 / 玩法事实仍按 `AGENTS.md` 中的权威文档顺序裁决；
2. “当前任务具体怎么做”以 `协同工作计划与验收反馈.md` 当前任务计划及最新验收反馈为准；
3. “长期先做什么、下一项是什么”以 `项目全量任务清单与协作节流指南.md` 为准；
4. 本文件只负责角色与流程，不覆盖具体任务契约；
5. 用户最新明确决策最高，规划与验收方应把决策写回正式协作文档后再继续。

## 12. 一句话恢复协议

新会话只要记住：

> **规划与验收方从第二份路线图选任务，把完整工单写进第一份协同文档；实施方只按第一份文档实施、填写实施记录并提交；规划与验收方独立验收，并且必须把“通过或退回”写回第一份文档的验收反馈；未通过绝不进入下一任务，通过后才更新第二份路线图并下发下一项。**
